01 / INTRODUCTION项目介绍

我们计划构建一个受 OpenCode 启发的轻量级终端 coding agent。目标是提供开箱即用的文本用户界面（TUI）：完成安装和模型 API 配置后，开发者即可打开代码仓库、描述编码任务、查看 agent 的操作和代码修改，并审阅最终结果，无需自行组装一套 agent 框架。初期面向小型 Python 代码仓库，支持修复 bug、实现范围明确的功能，以及根据测试反馈改进代码。我们将使用现有语言模型，不训练新的基础模型。

项目重点是 coding harness，即围绕模型构建、负责工具执行、反馈、上下文、状态和停止条件的软件系统。仅生成看似合理的代码还不够：agent 还需要找到相关文件、从失败的编辑操作中恢复，并验证自己的修改。我们希望通过自主实现一个精简系统、测量其运行表现，理解这些机制的内部原理。项目将 AI agent 设计与开发者工具结合，可能为软件维护和编程教育提供更易使用、过程可检查的自动化辅助。

在固定模型和执行预算下，可复用的任务指令（skills）与持久化项目记忆，会如何影响工具型 coding agent 的正确性和效率？

我们将区分产品易用性和编码能力：一个方便的 TUI 本身并不能证明 agent 完成任务的能力得到提升。

02 / RELATED WORK已有研究与拟开展的贡献

SWE-agent 工具交互

SWE-agent [1] 研究用于代码仓库导航、代码编辑与执行的 agent-computer interface。它的重要贡献是表明：提供给模型的交互接口会影响软件工程任务表现。我们认可它对工具反馈和交互设计的具体研究。不过，其软件修复场景本身并不能证明持久化项目记忆或指令型 skills 在不同任务类型中的收益。它将为我们的文件搜索、编辑和测试反馈循环提供参考。

OpenHands Software Agent SDK 模块化架构

OpenHands Software Agent SDK [2] 提供模块化的软件 agent 架构，涵盖工具、基于事件的状态管理、上下文处理，以及本地或远程执行。我们认可它将 agent 逻辑与执行基础设施分离的方式，以及包含 MCP 在内的扩展能力。它面向生产环境，范围大于我们的课程项目；直接采用完整系统，也会增加我们单独分析各项设计选择的难度。因此，我们将实现一个接口清晰、保留执行记录的较小 harness。

OPENDEV 上下文与记忆

OPENDEV [3] 描述一个原生终端 coding agent，包含规划与执行分离、按需发现工具、上下文压缩和跨会话项目记忆。这些内容与我们的用户体验和上下文管理目标直接相关。我们认可其详细的工程经验总结，但所引用的版本仍是进行中的预印本。一个组合架构的存在，并不意味着每个组件都会帮助我们的任务。因此，我们会分别测试选定的机制，而不是预设整套设计都会带来性能提升。

03 / METHODOLOGY方法与系统设计

我们的贡献是一个自主实现、过程可检查的原型，以及针对部分 harness 组件的对照评估，不声称发明 coding agent、MCP 或 skills。OpenCode 是产品灵感来源，上述三篇论文用于指导具体架构设计。若复用开源实现，将注明来源并遵守其许可证。目前尚未编写实现代码，也没有收集实验结果。

3.1 核心 harness 与终端体验

我们计划使用 Python 和 Textual 等 TUI 库。界面将展示对话历史、当前工具活动、测试输出和待审阅的代码 diff。一个轻量的模型适配层将连接支持工具调用的语言模型 API。执行循环接收任务后，请求模型生成下一步操作，验证工具参数，执行操作，将反馈加入上下文，然后继续，直到任务结束、达到配置的限制或被用户中断。任务状态和按时间排列的操作日志将支持检查过程和恢复会话。

用户任务 → 模型选择操作 → 验证参数 → 执行工具 → 接收反馈 → 继续或结束全过程记录任务状态、工具活动和代码变更。

初始工具包括列出仓库文件、搜索内容、读取指定范围的文件、以 patch 修改代码，以及执行测试。工具响应将包含结构化状态、相关输出和明确的错误信息。文件编辑限制在所选工作目录内；命令设置超时和输出长度限制；破坏性操作或访问工作区外的操作需要确认。评估将在一次性的隔离仓库副本中进行。通过可见测试将被报告为验证证据，而不会被视为所有需求均已满足的证明。

3.2 MCP 与可复用 skills

我们将实现一个 MCP 客户端适配器，并演示至少一个由 MCP server 提供的工具，与原生工具同时工作。两类工具共用内部工具注册表和参数验证机制，使 agent 循环无需依赖工具的具体部署方式。MCP 提供的是互操作性；我们不会假设仅采用该协议就能提高代码正确率。与直接写死的工具集成相比，这种设计需要额外处理协议和失败情形，但更便于替换工具。

Skills 将采用版本化的指令文件，描述“调查失败的测试”“验证代码补丁”等操作流程。Harness 提供简短的 skill 描述，并按需加载选中的详细指令。另一种方法是把所有指令都放进初始提示词，虽然简单，却可能浪费上下文并引入无关指导。我们选择按需加载。Skills 提供操作流程，不包含评估任务的答案；实验中将记录加载了哪些 skills，以及它们建议的检查是否真正执行。

3.3 记忆、上下文与可选的 agent 协作

我们会区分临时对话状态与持久化项目记忆。持久化条目记录测试命令、仓库结构和项目约定等事实，并保存来源与更新时间。最近的工具反馈和简短的进度摘要构成活跃上下文，较长的日志则保存在磁盘上，供后续检索。初期采用本地结构化存储，便于检查。向量检索适合更大的项目，但会增加索引维护和检索相关性错误，因此暂不作为第一版的必需组件。

最小交付版本采用单 agent。独立的规划或审查 agent 是扩展目标：它可能提供有价值的二次检查，但也增加费用和协作复杂度。实现分为四个阶段：可工作的 TUI 与工具循环；MCP 集成和 skills；记忆与会话恢复；评估与打包。我们优先完成可靠的端到端编码流程，而非复制 OpenCode 的所有功能。

04 / EVALUATION预期结果与评估计划

我们将围绕小型 Python 仓库准备 12 个范围明确的任务：4 个 bug 修复、4 个功能添加、4 个需要理解仓库约定或跨文件关系的修改。每个任务包含初始仓库快照、任务描述、可见测试和独立的隐藏验收测试。最终评估前冻结任务、测试和 skill 定义，使用另外的开发任务调整提示词。Agent 无法读取或修改隐藏验收测试。

四组配置：逐项检验 skills 与记忆的作用
组别配置目的
A基础工具型 harness建立基准表现
BA + skills观察可复用指令的作用
CA + 持久化项目记忆观察项目记忆的作用
DA + skills + 项目记忆观察组合后的表现

各组固定模型版本、采样设置、原生与 MCP 工具的可用性、上下文上限，以及每个任务的步骤和 token 预算。每组对每个任务运行两次，共计划 96 次运行。完整实验前先小规模试运行估算费用；若需缩小实验规模，会如实报告。资源允许时，再增加一次性生成代码的基线。

所有配置都获得相同的前置仓库熟悉机会。只有开启记忆的配置可以把这一阶段记录的项目事实带入正式任务，不得保留评估尝试中的答案、补丁或验收测试细节。每次实验从干净的仓库快照开始。我们将分别报告准备记忆与解决任务的成本，不把记忆准备当作免费的步骤。

主要指标是任务成功率：通过全部隐藏验收测试，且现有测试套件没有出现回归失败。次要指标包括输入与输出 token 总量、实际运行时间、工具调用次数、无效工具调用次数，以及测试失败与修复循环次数。我们保留执行轨迹和代码 diff，报告逐任务结果与总体成功率，并分析定位错误、重复无效操作、过期记忆和过早结束等失败类型。任务规模较小、每项仅重复两次，会限制结果的可推广性；我们不会据此宣称全面优于成熟 agent。

我们预期基础 harness 更适合测试反馈明确的局部 bug。Skills 可能改善操作流程的一致性，记忆可能减少重复探索项目约定的工作。但简单任务上的收益可能更小；无关 skills 或过期记忆可能增加错误和 token 消耗。跨文件修改与描述不充分的任务预计仍然较难。这些是待验证的假设，不是测得的结果。若某个机制降低表现，我们会分析其检索与上下文影响，而不是只报告成功案例。

最终交付物包括附带安装说明的 TUI 应用、可复现实验的运行程序与任务集，以及将实验结果和 harness 设计联系起来的报告。易用性检查覆盖全新环境安装、模型配置、打开仓库、完成一个小型编码任务、审阅 diff 和恢复已保存的会话。这些功能检查与 AI 能力评估分别报告。
